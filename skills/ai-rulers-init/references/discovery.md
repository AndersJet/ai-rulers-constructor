# 绿地与棕地发现

记录仓库形态、技术栈、开发/验证命令、安全、数据、API/外部集成、前端、交付与高风险边界。
只记录任务相关事实；缺少影响正确性或授权的必要决定时保留未决项，其余未知细节可省略。

绿地：从用户已批准的需求、ADR、技术和边界决定出发，以 approved 记录期望约束。
代码尚不存在不阻止规则生成；未经批准的选型和纯构想保持未决。规则可以约束未来实现，
但不能声称依赖、测试命令或部署设施已经存在。

棕地：从代码、配置、测试、现有文档提取 observed 事实，同时记录已批准的变更决定。
既有实现与决定冲突时分别保留并说明迁移方向，不把现有缺陷自动提升为强制规范。

## 业务边界证据

先读已有领域文档、spec、ADR，再沿相关入口、契约、数据写入和测试追踪业务链路。
概览主要边界，对有证据或明确风险的部分深入，不要求先建立全库地图。

| 发现内容 | 核对依据 |
| --- | --- |
| 职责、排除职责与术语 | 领域说明、业务入口、跨前后端的同一业务流程 |
| 业务不变量 | 已批准需求、状态转换、金额/权限/顺序约束及关键测试断言 |
| 数据所有权 | 写入入口、持久化接口、派生数据的更新与一致性要求 |
| 对外契约与消费者 | API、事件、任务或文件契约，调用方与消费者测试 |
| 跨边界失败行为 | 重试、重复消息、并发、部分失败及事务外副作用 |
| 验证依据 | 可观察结果、项目测试入口、验收场景及尚未覆盖的路径 |

目录不自动构成业务域；业务域不等于 backend 等规则领域，也不登记为 Git submodule
模块。数据写入权、代码维护责任和审批权限分别核对，不从目录名或最近提交者推断。
跨域直写等现有实现只作 observed 证据；未经批准不据此生成允许该行为的规则。
已有知识正文保留原归属，Profile 只保存必要事实和指针，不复制整份业务地图。

## 项目工作流与画像

Git 与 CI 工作流先读项目入口、已有工作流文档和配置。按本次任务需要发现默认与长期分支、
任务分支创建或复用、worktree、PR/MR、本地 hook 和检查、CI 触发与必需检查，以及观察、
诊断、合并的人机分工。有权威正文时在 Profile 保存事实、批准决定及指针，不复制第二份工作流。
remote 或工具默认不能证明分支保护、MR 权限或人员责任；证据不足保持未决，仅在任务实际
需要该决定时确认，不要求所有项目完成统一问卷，不预设单主线、Git Flow 或自动创建 MR。

项目组合使用外部工作流技能时，读取 [skill-interop.md](skill-interop.md)。按本轮阶段
发现完成标准、tracker/domain/Git 权威、工作区复用与隔离条件、分支起点与 upstream、
成果保存和恢复入口。已有地图先核对来源与已回答选择；仅记录影响当前动作的事实或缺口。

统一 Profile 使用“项目身份、命令、当前有效事实与约束、阻塞性未决问题”四节。
事实表为：内容 / 依据类型 / 证据 / 作用域 / 置信度；依据仅 observed 或 approved。
作用域用 registry 领域名（core、backend、database、frontend-web、frontend-app、security、delivery）。
证据写可定位文件/决定引用。未决表为：问题 / 重要原因 / 作用域 / 必需审阅人。
项目工作流指针放在当前有效事实表的适用作用域，由运行态 WORKFLOW 按任务读取；
core 适用于跨领域约定，CI 专属约定可归 delivery。提交策略与分支、PR/MR 和 CI 工作流分别记录。

从绿地进入实现后，用 reconcile 核对批准决定与实际代码，确认一致、批准变更或保留冲突。
不需要两套平行目录、两份 State 或把全部 approved 行机械替换成 observed。
